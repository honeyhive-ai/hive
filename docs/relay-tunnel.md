# Relay tunnel: phone ↔ host remote access (`hive-tunnel/1`)

Status: **draft for implementation**, protocol version 1. Open source (MIT),
like the rest of this repo. The key words MUST, MUST NOT, SHOULD and MAY are
used as in RFC 2119.

This spec lets the Hive iPhone app reach a `hive serve` home host through a
relay, with no Tailscale/VPN and no inbound port on the host. The relay
forwards bytes and can verify who may connect. It can't read, alter or forge
anything, and it can't impersonate either end.

It covers:

- §3 keys and identifiers, §4 the pairing link (v2), §5 the phone credential;
- §6 the relay endpoints: host registration and control, host accept, phone connect;
- §7 the end-to-end session (Noise), §8 stream multiplexing, §9 how the
  existing `hive serve` HTTP + SSE API ([ios-app.md](ios-app.md)) runs over it unchanged;
- §10 keepalives, timeouts and reconnects, §11 limits, §12 error codes;
- §13 renewal and revocation, §14 end-to-end encrypted push;
- §15 relay seams and configuration (open vs hosted), §16 host changes;
- §17 the security properties and what provides each one, §18 versioning;
- §19 the test vectors and the interop test plan, §20 open questions.

Product context, App Store, billing and the threat model live in the iOS
repository's `docs/DESIGN.md` (private repo `hive-ios`). This document is only
the open wire protocol.

**Golden vectors:** [`relay-tunnel/vectors.json`](relay-tunnel/vectors.json),
generated by [`relay-tunnel/gen`](relay-tunnel/gen/main.go) (Go, flynn/noise)
and checked independently by [`relay-tunnel/check-rust`](relay-tunnel/check-rust/src/main.rs)
(Rust, snow). Both agree byte for byte. See §19.

---

## 0. Scope and non-goals (v1)

In scope: one owner, their host(s), and phones paired by a host. The phone is
a client of the host's API. It isn't a workspace member and holds no workspace
keys.

Out of scope for v1, but the design leaves room for them:

- Phone-only team members. Credentials are per phone and issued by the host,
  so a later version can add a role claim. Even stream ids are reserved for
  host-initiated streams (§8).
- Multi-instance relay routing. v1 needs the phone's connect and the host's
  control connection to land on the same relay process (§15.4).
- Traffic padding. v1 hides content but not sizes or timing (§17.2).
- Rotating a host key without re-pairing.

The relay provides **reachability only**: no compute, models or storage of
content.

## 1. Overview

```
 phone (iOS app)                    relay (Go, honeyhive-ai/relay)            host (hive serve)
 ───────────────                    ─────────────────────────────             ─────────────────
                                    ◀── WSS /v1/tunnel/host ─────────────────  persistent control
                                        challenge / hello(sig) / welcome        connection (§6.2)
 WSS /v1/tunnel/connect?host=H ──▶
   challenge ◀──
   auth{cred, PoP sig} ──▶          verify cred against H's registered key,
                                    PoP, expiry, revocation, entitlement
                                    ── open{sid, pid} on control ──────────▶
                                    ◀── WSS /v1/tunnel/accept?sid=… ────────  data connection (§6.3)
   ready ◀──                        splice: binary frames copied 1:1
 ════════════ Noise_IK (phone = initiator) end-to-end through the splice ════════════▶
 ════════ mux frames (§8): OPEN/DATA/FIN … carrying HTTP requests and responses ═════▶
                                                                              tower oneshot into
                                                                              the existing axum
                                                                              router (§9)
```

There are two layers:

1. **Relay layer** (§6). Three WebSocket endpoints and JSON text frames. This
   layer handles who may reach the host, and nothing else.
2. **End-to-end layer** (§7–§9). Opaque to the relay: binary WebSocket
   messages, one Noise message each. Inside them, a small stream mux carries
   HTTP request and response semantics.

## 2. Conventions

- `b64u(x)` is base64url **without padding** (RFC 4648 §5). Decoders MUST
  reject padding and non-alphabet characters.
- `ctx(label, p1, p2, …)` = ASCII `"hive-tunnel/1 " + label` ‖ `0x00` ‖ `p1`
  ‖ `p2` ‖ …. Every `p` is fixed-length, so the concatenation is unambiguous.
  This is the domain separation for every signature and derivation.
- `HKDF(ikm, info, n)` = HKDF-SHA256 (RFC 5869) with salt = ASCII
  `"hive-tunnel/1"`, the given ASCII `info` and output length `n`.
- `SHA256` is FIPS 180-4. Ed25519 is RFC 8032 (pure). Signatures are verified
  in "strict" mode where the library offers it (`verify_strict` in
  ed25519-dalek; Go's `ed25519.Verify` is already strict enough).
- Times are Unix seconds (integer). Peers MUST tolerate ±300 s of clock skew
  wherever a time is compared.
- JSON is UTF-8. Unknown object members MUST be ignored. Senders MUST NOT emit
  duplicate keys. Verifiers of signed JSON (the credential) MUST reject
  duplicates. Field names are case-sensitive.
- Integers on the wire (frame headers) are big-endian.

## 3. Keys and identifiers

| Name | Type | Held by | Purpose |
|---|---|---|---|
| host signing key | Ed25519 | host only | signs credentials (§5) and the control challenge (§6.2) |
| host static key `hs` | X25519 | host only | Noise static. Its public half is pinned by the phone through the QR code |
| `host_id` | 22 chars | public | `b64u(SHA256(ctx("host-id", host_sign_pub))[0..16])`, self-certifying |
| phone auth key | Ed25519 | phone only | proof of possession (PoP) at the relay (§6.4) |
| phone static key | X25519 | phone only | Noise static. Host stores the public half at enrollment |
| `pid` | 22 chars | host assigns | `b64u(16 random bytes)`, stable per paired phone |
| pairing secret `ps` | 32 bytes | QR code | one-time enrollment secret (§4, §7.2) |
| push key | 32 bytes | host + phone | `HKDF(h_enroll, "push-key", 32)` (§14) |

- The host keeps its keys in `<HIVE_DATA_DIR>/tunnel/keys.json` (mode 0600).
  The phone keeps its keys in the Keychain (`kSecAttrAccessibleAfterFirstUnlockThisDeviceOnly`,
  not synced). The push key also goes to a Keychain access group shared with
  the Notification Service Extension.
- All private keys come from the OS CSPRNG. X25519 private keys are 32 raw
  bytes; clamping happens inside X25519, as in RFC 7748.
- The phone uses **two** keys because Noise needs X25519, while the relay
  needs a signature it can check. A Secure Enclave P-256 auth key is a
  possible v2 hardening (§20).

## 4. Pairing link v2

The v1 link stays valid: `hive://pair?url=<b64u(serverURL)>&token=<token>`.
v2 **adds** parameters, so a v1 app still pairs over the direct path and
ignores the rest.

| Param | Required | Value |
|---|---|---|
| `url`, `token` | when a direct path exists | unchanged (direct HTTP + bearer, [ios-app.md](ios-app.md)) |
| `v` | yes (v2) | `2` |
| `hid` | yes | `host_id` |
| `hs` | yes | `b64u(host static public key)`, 32 bytes, **the trust anchor** |
| `relay` | yes | `b64u(relay base URL)`, e.g. `https://relay.example.com` (may include a path prefix, no trailing `/`) |
| `ps` | yes | `b64u(pairing secret)`, 32 bytes |
| `exp` | yes | expiry of `ps` (Unix s). Default issue time + 600 |

Example (from the vectors):

```
hive://pair?url=aHR0cDovLzEwMC4xMDEuMTAyLjEwNDo4Nzg3&token=4f1c…aabb&v=2
  &hid=2LGZFj2lCKlo49_pwPzGjw&hs=rX2_Zzy_XPP_rKyNHdO0tEeMyKpm054V5n1xdD_gFzo
  &relay=aHR0cHM6Ly9yZWxheS5leGFtcGxlLmNvbQ&ps=GGzSn9ODtHFtphJFAOvwhBIns8-YMbiqpMRV0K2kWAI&exp=1793000600
```

Rules:

- A relay-only host omits `url` and `token`. A v1 app then fails to parse the
  link. That's acceptable: it shows "unsupported link" and the user updates.
- The phone MUST require `https` for `relay`. The only exceptions are debug
  builds and loopback hosts in tests. The host MUST refuse to print an `http`
  relay URL unless `--insecure-relay` is set.
- `ps` is derived into three independent values:
  `eid = b64u(HKDF(ps,"enroll-id",16))`, `tag = HKDF(ps,"relay-tag",32)` and
  `psk = HKDF(ps,"noise-psk",32)`. The relay learns `eid` and `tag`. It never
  learns `ps` or `psk`.
- The phone MUST reject a link with `exp < now − 300`.

## 5. Phone credential (`hpc1`)

The format is compact and modelled on the relay's `hrt1` entitlement token:

```
hpc1.<b64u(claims_json)>.<b64u(ed25519_sig)>
sig = Ed25519(host_sign_key, ASCII("hpc1." + b64u(claims_json)))
claims_json = {"hid":"<host_id>","pid":"<pid>","pk":"<b64u(phone auth pub)>","iat":<s>,"exp":<s>}
```

The signature covers the exact transmitted bytes, so no JSON
canonicalization is needed. Issuers SHOULD emit the keys in the order shown.

**Verification**, by the relay on every connect, in this order. Any failure
gives `unauthorized` (4001), except where noted:

1. Three `.`-separated parts. Prefix `hpc1`. The signature decodes to 64 bytes.
2. `hid` equals the `host` query parameter, and that host is registered (else
   `host_unknown` 4004).
3. The signature verifies against the registered host signing key.
4. The claims parse. `hid`, `pid` and `pk` are present and well-formed
   (`pk` is 32 bytes). No duplicate keys.
5. `iat ≤ now + 300`, `exp > now` (else `credential_expired` 4002), and
   `exp − iat ≤ 400 days` (relay cap). The comparison is strict and has no
   skew allowance: a credential whose `exp` equals `now` is expired.
6. `(hid, pid)` isn't revoked (else `revoked` 4003).

The host issues credentials with `exp = iat + 90 days` by default. Renewal is
in §13.1.

## 6. Relay layer

All three endpoints are WebSockets (RFC 6455) over TLS. The client MUST offer
the subprotocol `hive-tunnel.1`, and the relay MUST select it. Otherwise the
relay refuses the upgrade with HTTP 426. Paths are relative to the relay base
URL.

- **Text messages** carry JSON relay-layer messages. Each has a string `t` and
  is at most 8 KiB.
- **Binary messages** carry end-to-end bytes (§7). They are allowed only after
  `ready` (phone) or on an accept connection (host). Each is at most 65 535
  bytes; above that, the relay closes with code 1009.
- **Errors:** before closing, the relay sends
  `{"t":"error","code":"<code>","message":"<human text>"}` and then a close
  frame with the matching close code from §12 (reason = `code`). The relay
  sends at most one `error` text frame per connection, and MAY send it even
  after `ready` (it is the only text frame allowed in that direction then).
  Clients MUST treat the close code as authoritative and the `error` frame as
  optional, since it can be lost when the socket closes.
- Unknown `t` values MUST be ignored by both peers.

### 6.0 Discovery: `GET /v1/tunnel/info` (plain HTTPS)

`200 {"versions":[1],"push":true|false,"billing":"none"|"appstore"}`. A relay
with the tunnel disabled answers `404` (the default; see §15). The app uses
this to check a relay URL, to decide whether to offer push, and to decide
whether `not_entitled` (4006) should lead to the in-app subscription
(`appstore`) or to an "ask the relay operator" message (`none`).

Only the hosted build (§15.3) reports `"billing":"appstore"`. The open build
always reports `"none"`, so a self-hosted relay with `HIVE_RELAY_TUNNEL=open`
offers the same tunnel for free and the app shows no paywall for it.

### 6.1 Host keys and registration

There's no separate registration call. A host is registered the first time it
completes the control handshake (§6.2) with a `hostPub` the relay hasn't seen.
The relay:

1. checks `hostId == b64u(SHA256(ctx("host-id", hostPub))[0..16])`;
2. verifies the challenge signature;
3. asks the policy `Register(hostId, hostPub, reg)` (§15.1), where `reg` is the
   optional registration token from `hello`. The open default admits per
   `HIVE_RELAY_TUNNEL`. A hosted deployment may require a token or register
   the host as `pending`;
4. stores `{hostId, hostPub, createdAt, lastSeen}` durably. The store is
   included in the relay's backup; it's relay-only state.

Because `host_id` is a hash of the key, a registered `host_id` can't be
claimed with another key. The relay GCs hosts that are `pending` and haven't
been seen for 30 days.

### 6.2 Host control connection: `GET /v1/tunnel/host`

The host keeps exactly one of these open whenever remote access is enabled.

```
relay → host  {"t":"challenge","v":1,"nonce":"<b64u 32 random bytes>"}
host  → relay {"t":"hello","v":1,"hostId":"…","hostPub":"<b64u>","sig":"<b64u>",
               "reg":"<optional token>","agent":"hive-serve/1.16.0"}
               sig = Ed25519(host_sign_key, ctx("host-auth", hostId, nonce_raw32))
relay → host  {"t":"welcome","status":"active"|"pending","maxSessions":8,"push":true|false}
```

- `hello` MUST arrive within 10 s of the challenge (else `timeout` 4012).
- A second control connection for the same `host_id` **supersedes** the first.
  The old one is closed with `superseded` (4009). On 4009 a host MUST NOT
  reconnect sooner than 60 s, and SHOULD log loudly, because it means two
  processes share one key.
- `pending` is the right status for a host that is registered but not
  entitled: enrollment works (§6.4.2), but sessions don't.

Messages on an established control connection. Host requests carry an `id`
(≤ 64 chars) and get an `ack`:

| Direction | Message | Meaning |
|---|---|---|
| relay→host | `{"t":"status","status":"active"\|"pending"}` | entitlement changed |
| relay→host | `{"t":"open","sid":"<b64u 16>","mode":"session","pid":"…"}` | an admitted phone is waiting. Host attaches within 10 s (§6.3) or rejects |
| relay→host | `{"t":"open","sid":"…","mode":"enroll","eid":"…"}` | a phone is enrolling with that window |
| host→relay | `{"t":"reject","sid":"…","code":"host_rejected"}` | decline an `open` (e.g. at capacity) |
| host→relay | `{"t":"enroll","id":"…","eid":"…","tagHash":"<b64u SHA256(tag)>","exp":<s>}` | open an enrollment window, `exp ≤ now+900` |
| host→relay | `{"t":"enrollClose","id":"…","eid":"…"}` | close the window (used or cancelled) |
| host→relay | `{"t":"revoke","id":"…","pid":"…","exp":<s>}` | revoke `pid` until `exp`, the latest `exp` the host issued to it (§13.2) |
| host→relay | `{"t":"push","id":"…","pid":"…","ct":"<b64u>","prio":"high"\|"normal","collapse":"<opt ≤64>"}` | send an encrypted push (§14) |
| host→relay | `{"t":"deregister","id":"…"}` | forget this host, its revocations and push tokens, then close |
| relay→host | `{"t":"ack","id":"…","ok":true}` or `{"t":"ack","id":"…","ok":false,"code":"…"}` | result of a host request |

### 6.3 Host accept connection: `GET /v1/tunnel/accept?sid=<sid>`

The host dials this once per `open`. `sid` is 128-bit random, single-use,
bound to the `host_id` whose control connection received it, and valid for
10 s. That makes it a bearer capability, delivered only over the host's
authenticated control connection. On success the relay sends nothing on this
connection. It starts splicing (§6.5). An unknown, used or expired `sid` gets
4001.

### 6.4 Phone connect: `GET /v1/tunnel/connect?host=<host_id>`

```
relay → phone {"t":"challenge","v":1,"nonce":"<b64u 32>"}
```

#### 6.4.1 Session admission

```
phone → relay {"t":"auth","cred":"hpc1…","sig":"<b64u>",
               "apns":{"token":"<hex>","env":"production"|"development"}}   (apns optional)
               sig = Ed25519(phone_auth_key, ctx("phone-auth", host_id, nonce_raw32))
```

The relay then does the following. Any failure closes with the code shown.

1. Verify `cred` (§5).
2. Verify `sig` with `pk` from the claims (4001).
3. Check the host status is `active` (`not_entitled` 4006).
4. Check the host's control connection is up (`host_offline` 4008).
5. Check the limits (4029).
6. Store or refresh the `apns` token for `(hid, pid)` when present (`null`
   clears it).
7. Send `open{mode:"session", pid}` to the host.
8. When the accept connection attaches, send `{"t":"ready","sid":"…"}` and
   splice. If the host rejects, close with `host_rejected` 4010; if it
   doesn't attach within 10 s, close with `timeout` 4012.

#### 6.4.2 Enrollment admission

```
phone → relay {"t":"enroll","eid":"<eid>","tag":"<b64u(tag)>"}
```

The relay checks that an open window with that `eid` exists for the host, that
`SHA256(tag) == tagHash`, and that it hasn't expired. A window allows at most
5 attempts. The host status may be `pending`. Then it runs steps 4, 5, 7 and 8
of §6.4.1 with `open{mode:"enroll", eid}`.

A missing, expired, closed (`enrollClose`) or used-up window (more than 5
attempts), a wrong tag, and a malformed `enroll` all close with
`unauthorized` (4001). The relay can't tell these apart for the phone without
helping an attacker probe windows, so the phone MUST NOT present 4001 during
enrollment as "re-pair" or "bad credential". It presents **"pairing code
expired or already used"** and asks the owner to run `hive pair` again.

The relay MUST cap an enrollment-mode splice at 5 minutes and 4 MiB in total,
so a `pending` host can't use enrollment as a free tunnel. The phone then
reconnects in session mode.

### 6.5 Splice

- The relay copies each binary message from one side to the other
  **unchanged and in order**, with at most one message in flight per
  direction. It reads the next message only after the previous one was
  written, so TCP backpressure reaches the sender.
- A close on either side closes the other side with the same code. 1000 and
  1001 pass through as 1000.
- The relay MUST NOT inspect, buffer beyond one message, reorder, or inject
  binary messages. It MAY count bytes for metering.
- Text messages after `ready` are a protocol error (4000).

## 7. End-to-end session (Noise)

### 7.1 Construction

| Mode | Noise protocol name |
|---|---|
| session | `Noise_IK_25519_ChaChaPoly_SHA256` |
| enrollment | `Noise_IKpsk1_25519_ChaChaPoly_SHA256` with `psk = HKDF(ps,"noise-psk",32)` |

- **Initiator** = phone. **Responder** = host. The phone knows the responder
  static `hs` in advance, from the QR code.
- **Prologue** = `ctx("noise", host_id)`. This binds the session to the host
  the phone meant to reach.
- **Transport:** each Noise message, handshake or transport, is exactly one
  binary WebSocket message. The maximum Noise message is 65 535 bytes
  (Noise spec), plaintext ≤ 65 519.
- **Implementations:**
  - Rust: [`snow`](https://crates.io/crates/snow).
  - Go: [`flynn/noise`](https://github.com/flynn/noise) (relay tests only; the
    relay never terminates Noise).
  - Swift: a small HandshakeState / CipherState on CryptoKit
    (`Curve25519.KeyAgreement`, `ChaChaPoly`, `SHA256`, `HMAC<SHA256>`).
    Noise's ChaChaPoly nonce is 4 zero bytes ‖ the 64-bit **little-endian**
    counter. Noise's HKDF is its own HMAC chain, not RFC 5869 `HKDF`; don't
    substitute CryptoKit's `HKDF` inside Noise.
- **DH output:** an all-zero output (a low-order peer key) MUST abort the
  handshake.

  > **Implementation note.** Not every Noise library does this for you.
  > `snow` 0.9.6's default X25519 resolver does **not** reject an all-zero DH
  > output: a handshake against a low-order key completes. Implementations
  > MUST check every DH result themselves (in Rust, wrap the resolver's `Dh`
  > and fail with `snow::Error::Dh` when the output is 32 zero bytes; in
  > Swift, CryptoKit's `sharedSecretFromKeyAgreement` must be checked the same
  > way). [`check-rust`](relay-tunnel/check-rust/src/main.rs) demonstrates the
  > hazard and the check.

Why IK: the phone always knows the host key, so the handshake takes one round
trip. Both statics are authenticated, and the phone's static is encrypted on
the wire. Why `psk1` for enrollment: the psk is mixed into message 1, so the
host rejects a phone without `ps` before it sends anything. That rules out
anonymous handshakes against the host key.

### 7.2 Enrollment (`mode:"enroll"`)

```
msg1 phone→host  payload {"v":1,"name":"<≤64 chars>","pk":"<b64u phone auth pub>"}
msg2 host→phone  payload {"v":1,"pid":"<pid>","cred":"hpc1…"}
then transport; the phone MUST send a PING frame (§8) first
```

Host rules:

- **E1.** The window for `eid` must be open and unexpired. A failed decrypt
  of msg1 means a wrong `ps`: close and count the attempt.
- **E2.** The first phone static that completes msg1 **binds** the window. A
  different static on a later attempt is rejected.
- **E3.** The host creates the record `{pid, name, authPub = pk, staticPub,
  pushKey = HKDF(h,"push-key",32), enrolledAt}`, where `h` is the final
  handshake hash. It issues `cred` for `pk`. If the static is already paired
  to an **active** record, that record is replaced and keeps its `pid`. If
  the only record with that static was revoked, the phone gets a **new**
  `pid`: the revoked `pid` stays revoked at the relay until its `exp` (§13.2),
  so reusing it would lock the re-paired phone out.
- **E4.** The record becomes **active** only when the first valid transport
  message from the phone arrives. Only then does the host consume `ps` and
  send `enrollClose`. A replayed msg1 (for example, from the relay) can't
  produce that message.
- **E5.** After E4 the connection carries normal API traffic (§8, §9) under
  the relay's enrollment cap. The host SHOULD tell the owner: a terminal or
  log line, and a push to the other paired phones ("New phone paired: …").

The phone keeps `pid`, `cred`, the push key and the host's `hs`/`hid`/relay.

### 7.3 Session (`mode:"session"`)

```
msg1 phone→host  payload {"v":1}
msg2 host→phone  payload {"v":1}
```

Host rules:

- **S1.** The remote static revealed by msg1 MUST belong to an active,
  unrevoked phone record. Otherwise the host closes without sending msg2.
- **S2.** That record's `pid` MUST equal the `pid` in the relay's `open`. A
  mismatch means the relay or the credential is inconsistent: close and log.
- **S3.** The host performs no application action until it receives a valid
  transport message. The msg1 payload is replayable and has no forward
  secrecy, so it MUST NOT carry secrets or requests. This applies to both
  modes.

### 7.4 Session lifetime

A session MUST end after 24 h or 2³² transport messages in either direction,
whichever comes first. The host sends GOAWAY `lifetime` and the phone
reconnects. There's no in-session rekey in v1. Both sides erase the session
keys on close.

## 8. Stream multiplexing

Each Noise transport plaintext is **exactly one frame**:

```
+--------+----------------------+------------------+
| type u8| stream_id u32 (BE)   | payload …        |
+--------+----------------------+------------------+
```

| Type | Name | Stream | Payload |
|---|---|---|---|
| 0x01 | OPEN | ≠0 | request head, JSON (§9), ≤ 16 KiB. Phone→host only |
| 0x02 | DATA | ≠0 | body bytes, 1..16 384 |
| 0x03 | FIN | ≠0 | empty. The sender's half of the stream is finished |
| 0x04 | RESET | ≠0 | u32 code ‖ optional UTF-8 reason. Aborts both halves |
| 0x05 | RESPONSE | ≠0 | response head, JSON (§9), ≤ 16 KiB. Host→phone only |
| 0x06 | WINDOW | ≠0 | u32 increment (1..2³¹−1) |
| 0x07 | PING | 0 | 8 opaque bytes |
| 0x08 | PONG | 0 | the 8 bytes of the PING it answers |
| 0x09 | GOAWAY | 0 | u32 code ‖ optional UTF-8 reason. The sender closes the session after flushing |

- **Stream ids.** The phone opens streams with odd ids, strictly increasing
  from 1. Even ids are reserved for host-initiated streams in a later version.
  A v1 host MUST RESET any even-id OPEN with `refused`. Ids aren't reused
  within a session.
- **Lifecycle.**
  - Request: phone OPEN → DATA* → FIN.
  - Response: host RESPONSE → DATA* → FIN.
  - The stream is closed when both FINs have been sent, or on RESET from
    either side. Frames for a closed or unknown stream are ignored, except
    OPEN.
- **Flow control** works per stream and per direction. The initial send
  window is 262 144 bytes. DATA payload bytes consume it; WINDOW adds to it.
  Heads and control frames aren't counted. A receiver SHOULD send WINDOW once
  it has consumed half the window. DATA beyond the window gets RESET
  `flow_control`. A sender MAY split a body into DATA frames of any size
  from 1 byte up to 16 384 bytes to fit the remaining window; it MUST NOT send
  an empty DATA frame and waits for WINDOW when the window is 0. A WINDOW that
  would raise the send window above 2³¹−1 is a flow-control error: the
  receiver of that WINDOW sends RESET `flow_control` on the stream. There's no session-level window: the transport's ordered
  backpressure (§6.5) bounds the total.
- **Limits.** At most 32 concurrent open streams per session. An OPEN beyond
  that gets RESET `refused`.
- **Forward compatibility.** Unknown frame types MUST be ignored. A malformed
  frame (short header, bad length, OPEN from the host, RESPONSE from the
  phone, or bad JSON in a head) gets RESET `protocol` on its stream, or
  GOAWAY `protocol` on stream 0.

## 9. HTTP over the mux

The existing API runs unchanged. The mux carries HTTP **semantics**, not
HTTP/1.1 bytes.

Request head (OPEN):

```json
{"method":"GET","path":"/v1/events","headers":[["accept","text/event-stream"],["last-event-id","42"]]}
```

Response head (RESPONSE):

```json
{"status":200,"headers":[["content-type","text/event-stream"]]}
```

- `path` is the request target: the path **and the query string**, if any
  (`/v1/events?since=42`), percent-encoded as in an HTTP/1.1 request line.
  There is no separate query member and no fragment.
- Header names are lowercase. Repeated names are allowed. Values are strings.
- Hop-by-hop headers (`connection`, `keep-alive`, `transfer-encoding`, `te`,
  `upgrade`, `host`, `proxy-*`) MUST NOT be sent and MUST be dropped on
  receipt.
- The body is the DATA bytes, already de-chunked. It ends at FIN.
  `content-length` is optional and informative.
- An SSE response stays open, sending events as DATA. The phone cancels it
  with RESET `cancel`.

Host connector (`hive serve`):

- `path` MUST start with `/v1/`; anything else gets a `404`.
- The connector builds an `http::Request` and calls the axum router
  **in process**, with `tower::ServiceExt::oneshot`. There's no socket, so
  remote access works even when the direct listener is bound only to
  loopback.
- It **removes** any `authorization` header and inserts the request
  extension `TunnelPeer { pid }`. The auth middleware treats `TunnelPeer` as
  authorized. On each request it re-checks that `pid` is still active, so a
  revocation takes effect immediately even on an open session.
- Tunnel-only routes are served when `TunnelPeer` is present. With a bearer
  token they return `404`:
  - `POST /v1/tunnel/credential` → `{"credential":"hpc1…","exp":<s>}`: a fresh
    credential for the same `pid` and `pk` (§13.1);
  - `PUT /v1/tunnel/push` `{"enabled":bool,"previews"?:bool}` →
    `{"enabled":bool,"previews":bool}`: whether this phone wants pushes, and
    whether they carry a message preview (§14). `previews` defaults to `true`
    for a newly paired phone; when the field is absent the stored value is
    kept.

Phone client: the transport layer maps each `URLRequest` onto one stream and
builds an `HTTPURLResponse` and body or byte sequence from the reply. In the
iOS app that's one more implementation of its `HiveTransport` protocol (the
abstraction the direct and demo transports already share; a `URLProtocol`
would also work). The API client, the SSE parser and `Last-Event-ID` resume
are unchanged.

## 10. Keepalives, timeouts, reconnects

| What | Value |
|---|---|
| Relay WebSocket ping | every 20 s on every tunnel socket. A peer silent (no frame, no pong) for 60 s is closed (`timeout`) |
| End-to-end PING | either side PINGs once it has received nothing **and** sent nothing for 25 s (the phone MUST; the host MAY, since its idle rule below covers it). No PONG within 10 s → drop the session (the phone reconnects). This detects a relay that black-holes traffic. Both sides MUST answer PING with PONG |
| Host idle | close a session with GOAWAY `normal` after 90 s with no frame from the phone, **only while it has no open streams**. An open SSE stream is not idle |
| Handshake | must complete within 10 s of `ready` (both ends) |
| `hello` / `auth` after challenge | 10 s |
| `open` → accept attached | 10 s |
| Phone reconnect | backoff 1, 2, 4 … 30 s, ±20 % jitter. No automatic retry on 4001/4002/4003/4006: the app shows the cause instead |
| Host control reconnect | backoff 1 … 60 s, ±20 % jitter. 4009: wait ≥ 60 s |
| Relay shutdown | close every tunnel socket with `shutting_down` (4011). Clients retry with backoff |

After a reconnect, the phone's SSE resumes with `Last-Event-ID` exactly as on
the direct path.

Go implementers: the relay's `http.Server` read and write timeouts (30 s)
also apply to hijacked WebSocket connections. Clear the deadlines after the
upgrade, and use ping/pong deadlines instead.

## 12. Error codes

Relay close codes, sent with `{"t":"error","code":…}` first:

| Close | `code` | Meaning | Client action |
|---|---|---|---|
| 4000 | `protocol` | malformed or unexpected message | bug: log, back off |
| 4001 | `unauthorized` | bad credential, PoP, host signature, `sid` or tag | phone: re-pair. host: stop and log |
| 4002 | `credential_expired` | `exp` passed | phone: re-pair, or renew over the direct path |
| 4003 | `revoked` | `pid` revoked | phone: forget the host, show it |
| 4004 | `host_unknown` | no such registered host | phone: show it |
| 4006 | `not_entitled` | host is `pending`/suspended | phone: show the subscription screen |
| 4008 | `host_offline` | no control connection | retry with backoff, show "host offline" |
| 4009 | `superseded` | a newer control connection for this host | host: wait ≥ 60 s |
| 4010 | `host_rejected` | host declined `open` | retry with backoff |
| 4011 | `shutting_down` | relay restarting | retry with backoff |
| 4012 | `timeout` | a deadline in §10 passed | retry with backoff |
| 4026 | `unsupported_version` | `v` not supported | update the app or host |
| 4029 | `rate_limited` | §11 | back off ≥ 30 s |
| 1009 | (WS standard) | message too big | bug |
| 1011 | `internal` (WS standard) | relay-side failure, e.g. its store is unreachable | treat like 4011: retry with backoff |

Mux RESET codes: 0 `cancel`, 1 `refused`, 2 `protocol`, 3 `flow_control`,
4 `internal`.

GOAWAY codes: 0 `normal`, 1 `revoked`, 2 `protocol`, 3 `lifetime`,
4 `shutting_down`.

HTTP status codes inside streams are the API's own ([ios-app.md](ios-app.md)).

### 12.1 Relay behaviour where v1 was silent

The reference relay ([`honeyhive-ai/relay`](https://github.com/honeyhive-ai/relay),
Go) made these choices where the text above didn't decide. Other relays
SHOULD behave the same, and clients MUST tolerate them:

- **Store failure.** If the relay can't read or write its tunnel store while
  admitting a host or phone, it closes with **1011** `internal`. A failing
  `revoke` or `deregister` write is acked `ok:false, code:"internal"`, and the
  host retries.
- **Enrollment caps (§6.4.2).** When an enrollment-mode splice reaches its
  time cap, both sides are closed with **4012** `timeout`; at its byte cap,
  with **4029** `rate_limited`. Either way the phone reconnects in session
  mode with the credential it just received.
- **Enrollment window acks.** `enroll` is acked `ok:false` with
  `window_too_long` (`exp` beyond now + 15 min, past skew), `expired` (`exp`
  not in the future), `rate_limited` (2 windows already open) or `protocol`
  (malformed). Re-sending an open `eid` updates it and keeps its attempt count.
- **Deregister.** The relay forgets the host and closes its live phone
  sessions with **4004** `host_unknown`, acks, then closes the control
  connection with 1000. Later connects for that `host_id` get 4004 until it
  registers again.
- **Admission policy.** A host the policy doesn't admit (for example, not on
  the `allowlist`, or `Register` refused) is closed with **4001**
  `unauthorized` on the control connection; a host stops on 4001 (§12). A
  phone enrolling with such a host gets 4006.
- **Version.** A `hello` with `v` missing is treated like an unsupported `v`:
  **4026**.
- **Bad `host` parameter.** A `connect` whose `host` isn't a well-formed
  `host_id` gets 4004.
- **Close-code passthrough (§6.5).** 1000 and 1001 pass through as 1000.
  Codes 3000–4999 and 1002, 1003, 1007, 1008, 1009 and 1011 pass through with
  their reason. Anything else, including a connection dropped without a close
  frame, is relayed as 1000. A message over the size limit closes the sender
  with 1009 and the other side with 1009.
- **Times.** `exp > now` checks are strict (`exp == now` is expired). A
  `revoke` whose `exp` is already past isn't stored, but the phone's push
  token is still deleted and its live splices are still closed with 4003.
- **Error frame.** The relay sends at most one `{"t":"error"}` text frame
  before a close, including on a spliced connection after `ready`. It is
  advisory; the close code decides.

## 13. Renewal and revocation

### 13.1 Renewal

The phone calls `POST /v1/tunnel/credential` over the tunnel when its
credential's `iat` is more than 24 h old. It replaces the stored credential
only after the new one parses and has a later `exp`. The route is tunnel-only by design: the direct path's
shared bearer token doesn't identify a phone. An expired credential therefore
can't be renewed through the relay, and the phone has to re-pair. With a
90-day lifetime and daily renewal, this only happens to a phone that stayed
unused for 90 days.

### 13.2 Revocation

`hive phones revoke <pid|name>` on the host:

1. marks the record revoked (`phones.json`). From then on S1 rejects that
   phone's handshakes, and TunnelPeer re-checks reject its requests. **The
   host is authoritative, and this takes effect immediately**;
2. sends GOAWAY `revoked` on the phone's live sessions and closes them;
3. sends `revoke{pid, exp}` to the relay and retries until it's acked. The
   pending revocation is persisted, so it survives a restart. The relay then
   rejects that phone's connects with 4003 before they reach the host, kills
   its live splices and deletes its push token. It keeps the entry until
   `exp`;
4. by default also rotates the direct-path bearer token (`serve.token`),
   because a stolen phone holds that too. `--keep-token` opts out.

`hive remote reset` generates new host keys, so a new `host_id`: every phone
must re-pair. Use it if the host key may have leaked.

## 14. End-to-end encrypted push

The host encrypts and the relay forwards ciphertext to APNs. Only the hosted
relay can push to the App Store app, because it holds the APNs key. An open
relay without a `PushSender` acks `push` with `ok:false, code:"push_unavailable"`,
and the host falls back to ntfy if that's configured.

```
plaintext = {"v":1,"seq":<u64>,"ts":<s>,"kind":"message.done"|"proposal.created"|"phone.paired"|"test",
             "chatId"?:"…","proposalId"?:"…","title":"<≤64 bytes>","body":"<≤512 bytes>",
             "sender"?:"<≤64 bytes>","preview"?:true}
nonce     = 12 random bytes
ad        = ctx("push", host_id, pid)
ct        = b64u(nonce ‖ ChaCha20-Poly1305(push_key, nonce, plaintext, ad))     (raw ≤ 2 048 bytes)
```

**Previews (on by default).** Each phone has a `previews` preference (§9,
`PUT /v1/tunnel/push`, default `true`). The NSE shows `title` and `body` as
they are; the host decides what goes in them:

- `previews` on: `body` is a short preview of the content: for
  `message.done`, the first 120 characters of the message text (Unicode
  scalar values; whitespace runs collapsed to one space, control characters
  dropped, cut on a character boundary, `…` appended when cut, so at most
  121 characters); for `proposal.created`, the proposal title, cut the same
  way. `"preview":true` is set.
- `previews` off (sender only): `body` is empty and `preview` is absent.
  `title` still names the sender ("coder replied").

`title` names the sender and the event ("coder replied", "coder hit an error",
"Change ready for review") and `sender` is the agent or author name alone,
both cut on a character boundary to 64 bytes. Neither ever contains message
text. The preview is end-to-end encrypted like everything else: Apple and the
relay see only `ct`. If the encrypted push would exceed 2 048 bytes, the host
sends it without the preview instead.

- `seq` increases strictly per `(host, pid)` and survives restarts.
- The relay sends APNs `apns-push-type: alert`, priority 10 (`high`) or 5
  (`normal`), `apns-expiration` now + 1 h, and `apns-collapse-id = collapse`
  when present. The payload:
  `{"aps":{"alert":{"title":"Hive","body":"New activity on your host"},"mutable-content":1},"hive":{"v":1,"hid":"…","pid":"…","ct":"…"}}`.
- The Notification Service Extension:
  1. decrypts with the push key for `(hid, pid)`;
  2. accepts the notification only if `|ts − now| ≤ 3600` and `seq` is greater
     than the last seen `seq` (kept in the App Group);
  3. then replaces the title and body and sets the deep link
     `hive://chat/<chatId>`.

  On any failure it leaves the generic text. A relay can therefore suppress,
  delay or replay pushes, but a replay shows only the generic text.
- `collapse` is opaque. Hosts SHOULD use `b64u(HMAC-SHA256(push_key, chatId)[0..12])`
  so the relay can't link it to a chat id.

**Self-hosted relays and push.** APNs accepts pushes for the App Store app
only when they're signed with that app's APNs key, which only the publisher
holds. A self-hosted open relay therefore has no `PushSender`, reports
`"push":false`, and acks host pushes `push_unavailable`; hosts fall back to
ntfy. A possible later addition (not part of v1): an optional push gateway on
the hosted service that accepts the same `{hid, pid, token, env, ct, prio,
collapse}` from a registered self-hosted relay and forwards it to APNs. It
would see only ciphertext, as the hosted relay does today.

## 15. Relay seams and configuration

### 15.1 Seams (Go, `honeyhive-ai/relay`)

```go
type HostStatus struct { Active bool; MaxSessions int } // !Active == "pending"

// TunnelPolicy admits host registrations and reports entitlement. nil = TunnelPolicyFromEnv().
type TunnelPolicy interface {
    Register(ctx context.Context, hostID string, hostPub ed25519.PublicKey, regToken string) error
    Status(ctx context.Context, hostID string) (HostStatus, error) // relay caches ≤ 60 s
}

// PushSender delivers an already-encrypted push. nil = push unavailable.
type PushSender interface {
    Send(ctx context.Context, hostID, pid string, token PushToken, ct []byte, prio, collapse string) error
}
```

The store additions go in both backends (memory/snapshot and Postgres) and
are included in the backup:

- tunnel hosts `(host_id, pub, created_at, last_seen)`;
- revocations `(host_id, pid, exp)`;
- push tokens `(host_id, pid, token, env, updated_at)`.

### 15.2 Open build (env)

| Var | Meaning |
|---|---|
| `HIVE_RELAY_TUNNEL` | `off` (**default**: `/v1/tunnel/*` → 404), `open` (any host may register and is `active`), `allowlist` (only `HIVE_RELAY_TUNNEL_HOSTS`) |
| `HIVE_RELAY_TUNNEL_HOSTS` | comma-separated `host_id`s for `allowlist` |

When the relay's existing entitlement gate is configured
(`HIVE_RELAY_TOKEN_PUBKEY` / `HIVE_RELAY_ACCESS_TOKENS`), `Register` also
requires `regToken` to pass that `EntitlementVerifier`. This reuses `hrt1`
operator tokens.

The default is `off`. A relay deployed today does **not** become a public
tunnel provider by upgrading.

### 15.3 Hosted build

A private downstream binary (`honeyhive-ai/hive-cloud`) imports the relay
package and injects:

- a `TunnelPolicy` backed by App Store entitlements. Hosts register as
  `pending`; a host becomes `active` while a subscription is bound to it;
- an APNs `PushSender`;
- its own bind and App Store routes under `/v1/remote/` and `/v1/appstore/`.

It runs on the same deployment as the public open sync relay, so it MUST be
a strict superset of the open binary:
every open `/v1` route, the admin routes, `hrt1` tokens, storage and env
behave exactly as in `cmd/hive-relay`. The relay enforces this through
`relay.MainWith(Extension)`: an extension can only set the tunnel seams, add
routes under unused `/v1/<name>/` prefixes and add subcommands, and a failing
extension falls back to the open relay rather than failing closed. The
enterprise (fail-closed) binary MUST NOT be deployed to that app.

### 15.4 One process per host

v1 keeps live control connections in process. A deployment MUST run one
instance, or route `/v1/tunnel/connect?host=H` and `/v1/tunnel/accept` to the
instance that holds H's control connection. On Fly that can be `fly-replay`
from a Postgres `host_id → machine` row. That's a later phase, and the wire
protocol doesn't change.

### 15.5 Applying a policy change at once (optional)

The relay caches `TunnelPolicy.Status` for up to 60 s, so by default a
change (a purchase bound to a host, a subscription that lapsed, a refund, an
operator editing an allowlist) takes effect within a minute. An operator
whose policy changes out of band can call

```go
func (s *Server) RefreshTunnelStatus(hostID string)
```

after the change. It drops the cached status, so the next phone connect asks
the policy again, and re-checks a connected host at once, sending it
`{"t":"status"}` if the status changed. It's a no-op when the tunnel is off,
safe from any goroutine, and doesn't change the wire protocol. A hosted build
calls it right after binding or unbinding a subscription.

## 16. Host changes (`hive serve`), summary

- New module `crates/hive-cli/src/serve/tunnel/`: keys, phones, the control
  client (tokio-tungstenite + rustls), sessions (snow), mux and connector.
- State lives in `<HIVE_DATA_DIR>/tunnel/`, all files 0600: `keys.json`,
  `phones.json`, `relay.json`, and `pending/` for enrollment windows and
  revocations.
- **CLI:**
  - `hive remote enable --relay <url> [--reg-token T]`, `hive remote status|disable|reset`;
  - `hive pair` prints the v2 link when remote access is enabled (`--relay-only`
    omits `url`/`token`);
  - `hive phones list|revoke`.

  `hive pair` and `hive phones` run as separate processes. They write
  `pending/` files, and `hive serve` picks them up within 2 s. This is the
  same file-handoff model as `serve.token`.
- **API:** the auth middleware accepts `TunnelPeer`, plus the tunnel-only
  routes (§9). No handler changes.

## 17. Security properties

### 17.1 What the design provides

| # | Property | Mechanism | Test (§19.3) |
|---|---|---|---|
| P1 | Relay can't read phone↔host traffic | Noise IK transport keys from `es, ss, ee, se`. The relay never holds `hs` or the phone static | T-relay-canary |
| P2 | Relay can't alter, reorder, drop or inject undetected | ChaChaPoly AEAD with counter nonces. Any failure ends the session | T-mitm-mutate |
| P3 | Phone talks only to the real host | `hs` pinned from the QR code; IK fails unless the responder holds `hs` | T-impostor-host |
| P4 | Host serves only phones it paired | phone static ∈ active records (S1). Enrollment needs `psk` from `ps` (E1) | T-unknown-static |
| P5 | Unpaired phones never reach the host | relay verifies `hpc1` (host-signed) plus PoP over a fresh challenge before `open` | T-relay-gate |
| P6 | Relay can't mint credentials or enroll phones | Ed25519 host key and `ps`/`psk` never reach the relay. `tag`/`eid` are HKDF-separated from `psk` | T-forged-cred, T-relay-enroll |
| P7 | No one can take over a `host_id` | `host_id = H(host_sign_pub)` plus a signed challenge per control connect | T-hostid-claim |
| P8 | Forward secrecy for session traffic | ephemeral `ee`; keys erased on close; 24 h lifetime | review |
| P9 | Replay resistance | fresh challenge per connect; host acts only after a transport message (S3, E4); single-use `ps`; Noise nonces; push `seq`/`ts` | T-replay |
| P10 | A captured pairing QR expires and is single-use | `exp` ≤ 15 min; bound to the first static (E2); consumed at E4; owner notified (E5) | T-qr-reuse |
| P11 | Revocation | host-authoritative and immediate (S1, per-request re-check); relay-side denylist for DoS and push | T-revoke |
| P12 | Push content is hidden from relay and Apple | ChaChaPoly with the push key derived from the enrollment handshake hash; AD binds `hid` and `pid` | T-push |
| P13 | No downgrade | single suite; version in the protocol name, prologue, subprotocol and `ctx` strings; no negotiation | T-version |
| P14 | Cross-host confusion | the prologue binds `host_id`; S2 checks `pid` consistency | T-wrong-prologue |

### 17.2 What it doesn't provide (accepted for v1)

- **Metadata.** The relay sees IPs, `host_id`, `pid`, connect times, message
  sizes and timing (so it could infer streaming activity), APNs tokens and
  push counts.
- **Availability.** A malicious or compromised relay can drop everything,
  suppress pushes or replay old ones (shown as generic text). Those are all
  denial-of-service. The phone's direct path (Tailscale/LAN) is the fallback.
- **KCI and secrecy of msg1.** IK msg1 isn't forward secret, so its payload
  carries nothing secret (S3).
- **Compromise of either endpoint.** A stolen, unlocked, jailbroken phone
  leaks its keys until revoked. A compromised host is game over.
- **TLS** to the relay protects only relay-layer metadata (the credential,
  PoP and APNs token). Content security never depends on it.

## 18. Versioning

The version is `1` in all of these:

- WebSocket subprotocol `hive-tunnel.1`;
- path prefix `/v1/tunnel`;
- `"v":1` in relay messages and Noise payloads;
- the `ctx` and HKDF salt strings `hive-tunnel/1`;
- the credential prefix `hpc1`;
- pairing link `v=2` (link format version, independent).

Additive JSON fields, new `t` values and new frame types are compatible,
because receivers ignore what they don't know. Anything else is version 2:
new strings everywhere, and relays MAY serve both. `GET /v1/tunnel/info`
lists the supported versions.

## 19. Test vectors and interop test plan

### 19.1 Vectors

[`relay-tunnel/vectors.json`](relay-tunnel/vectors.json) is deterministic.
Every secret is `SHA256("hive-tunnel test " + label)`.

| Key | Contents |
|---|---|
| `keys` | host signing seed and pub, host static priv/pub, phone auth seed and pub, phone static priv/pub |
| `hostId`, `pid` | `2LGZFj2lCKlo49_pwPzGjw`, `lg7S2X1oS18S3AUMgTzRgQ` |
| `challenge` | nonce, exact `ctx` inputs and signatures for host-auth and phone-auth |
| `credential` | exact `claimsJson` and the resulting `hpc1` token |
| `pairing` | `ps`, `eid`, `tag`, `tagHash`, `psk`, and a full v2 link |
| `enrollment` | IKpsk1 transcript: ephemerals, msg1/msg2 payloads and bytes, handshake hash, push key, PING/PONG transport messages |
| `session` | IK transcript plus a full `GET /v1/health` exchange (OPEN, FIN, RESPONSE, DATA, FIN) as plaintext and wire bytes |
| `push` | plaintext, AD, nonce and `ct` under the enrollment push key |
| `negative` | a credential with altered claims, a session msg2 with one bit flipped, and a msg1 built for another host's prologue. Each MUST be rejected |

How to reproduce the transcripts with injected ephemerals:

- **Rust:** `snow::Builder::fixed_ephemeral_key_for_testing_only`.
- **Go:** flynn/noise reads the ephemeral from `Config.Random`; its
  `EphemeralKeypair` field is used only for pre-messages and does **not**
  work for this. Note also that both sides return `(cs1, cs2)`, where `cs1`
  encrypts initiator→responder.
- **Swift:** a test-only initializer that takes the ephemeral.

**Ed25519 in Swift:** CryptoKit's Ed25519 signatures are randomized (checked:
two signatures over the same input differ). Swift tests therefore **verify**
the vector signatures and their own signatures; they don't compare bytes. Go
and Rust signatures are deterministic and MUST match byte for byte.

Regenerate and cross-check:

```sh
cd docs/relay-tunnel/gen && go run . | diff - ../vectors.json       # Go (flynn/noise)
cd docs/relay-tunnel/check-rust && cargo run -q -- ../vectors.json  # Rust (snow): asserts every value
```

### 19.2 Conformance per implementation

Each of Rust (host), Go (relay, plus a test-only reference phone and host)
and Swift (phone) MUST pass:

1. **V-keys:** derive both public keys, `host_id`, `eid`, `tag`, `tagHash`
   and `psk`.
2. **V-cred:** verify the `hpc1` token. Reject `negative.credentialTamperedClaims`.
   Reject the same token with `exp` in the past, with `hid` ≠ the `host`
   query, with padding added to a segment, and with a duplicate `"exp"` key.
3. **V-noise:** reproduce `msg1Hex`, `msg2Hex`, `handshakeHashHex` and every
   `wireHex`, as initiator and as responder, in both modes. Reject
   `negative.sessionMsg2TamperedHex` and `negative.sessionMsg1OtherHostPrologueHex`.
   Reject an all-zero DH result (peer static = 32 zero bytes).
4. **V-mux:** encode and decode the vector frames. A fuzz target for the
   frame parser and the flow-control state machine runs ≥ 10 min in CI with
   no panic. Exceeding the window gives RESET 3. An even-id OPEN gives RESET 1.
5. **V-push:** decrypt `push.ct`. Flipping one bit of `ct` or of the AD fails.

### 19.3 Integration tests

They use the real Go relay binary, built from a pinned commit in CI.

- **T-relay-gate:** a connect with no `auth`, a bad PoP, a credential from
  another host's key, an expired credential or a revoked `pid` is closed with
  the right code, and the host never sees an `open`.
- **T-relay-canary:** a phone sends a message containing a random canary.
  Relay byte captures (a test hook in the splice) never contain the canary or
  its JSON.
- **T-mitm-mutate:** a test relay mode flips a bit, drops a message,
  duplicates one, swaps two, or replays an old one. Each time both ends close
  the session, and no corrupted HTTP response reaches the client.
- **T-impostor-host:** the relay routes a phone to a second host with a
  different `hs`. The phone aborts at msg2 and shows "host identity changed".
- **T-unknown-static:** a valid credential plus PoP, but a different Noise
  static. The host closes without msg2.
- **T-forged-cred / T-relay-enroll:** the relay holds `eid`/`tag` but not
  `ps`. Its enrollment attempt fails at msg1, and the attempt is counted.
- **T-hostid-claim:** a hello with someone else's `hostId` and our own
  `hostPub` gives 4001.
- **T-replay:** replaying a recorded phone msg1 to the host produces a msg2
  and nothing else: no state change and no request executed. Replaying an
  old `auth` against a new challenge gives 4001.
- **T-qr-reuse:**
  - after E4, a second enrollment with the same `ps` fails;
  - a different static on an unconsumed window fails;
  - after `exp`, the window is gone (4001).
- **T-revoke:** a live SSE session ends within 1 s of `hive phones revoke`.
  Reconnect gives 4003. A request on a pre-revocation session gives 401.
- **T-push:** a host push reaches a fake `PushSender`. Its `ct` decrypts with
  the phone's key and with nothing the relay holds.
- **T-version:** a wrong subprotocol gives 426, and `"v":2` in hello gives 4026.
- **T-wrong-prologue:** a phone with the right `hs` but the wrong `hid` fails
  the handshake.
- **T-api-parity:** the existing `hive serve` integration suite (auth aside)
  also runs through the tunnel connector. Same results, including
  `Last-Event-ID` replay and `message.delta` streaming.
- **T-backpressure:** a phone that stops reading a 50 MB response stream
  keeps relay memory per session ≤ 2 messages and host buffering ≤ the window.
